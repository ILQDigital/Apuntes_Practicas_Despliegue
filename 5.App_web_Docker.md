# Despliegue de una Aplicación Web Python en Docker (VPS)

Esta guía explica paso a paso cómo empaquetar una aplicación web (en este ejemplo, construida con Python) dentro de un contenedor **Docker**, cómo mantener la persistencia de datos mediante **volúmenes** y cómo exponerla públicamente de forma segura utilizando **Cloudflare Tunnel**.

> [!NOTE]
> Todos los comandos de construcción y despliegue se ejecutan dentro del **VPS** tras acceder por SSH (ver [1.VPS.md](1.VPS.md)).

---

## 1. Localizar el punto de entrada y el puerto

Antes de crear el contenedor, debes identificar cómo arranca la aplicación y por qué puerto escucha.

1. Abre el script de Python que inicia el servidor (habitualmente llamado `app.py`, `main.py` o `server.py`).
2. Busca la línea donde se levanta el servidor web. Por ejemplo:
   - **Flask:** `app.run(host='0.0.0.0', port=8080)`
   - **FastAPI / Uvicorn:** `uvicorn.run(app, port=8080)`
   - **http.server (estándar):** `HTTPServer(('0.0.0.0', 8080), ...)`
3. Anota los dos datos clave:
   - **Archivo de inicio:** p. ej., `server.py`
   - **Puerto de escucha:** p. ej., `8080`

---

## 2. Crear el `Dockerfile`

En la raíz del proyecto, crea un archivo llamado `Dockerfile` (sin ninguna extensión de archivo).

### Plantilla general

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY . .
EXPOSE PUERTO
CMD ["python3", "app.py"]
```

### Ejemplo concreto

Si la aplicación no requiere librerías externas de terceros (utiliza la biblioteca estándar de Python), el `Dockerfile` resulta mínimo:

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY . .
EXPOSE 8080
CMD ["python3", "server.py"]
```

> [!TIP]
> **¿Y si usas librerías externas (`pip`)?**  
> Si tu proyecto requiere dependencias (como `flask`, `requests`, `pandas`, etc.), añade la instalación del archivo `requirements.txt` antes de copiar todo el código:
> ```dockerfile
> FROM python:3.12-slim
> WORKDIR /app
> COPY requirements.txt .
> RUN pip install --no-cache-dir -r requirements.txt
> COPY . .
> EXPOSE 8080
> CMD ["python3", "server.py"]
> ```

---

## 3. Subir la carpeta al VPS

Puedes transferir los archivos de la aplicación a la máquina virtual mediante dos métodos:

### Opción A: Transferencia mediante `scp` (Directa desde tu PC)

Desde la terminal de tu equipo local:

```bash
scp -r carpeta-app usuario@ip_vps:~/nombre_carpeta
```

### Opción B: Mediante Git y GitHub (Recomendado)

Subir el proyecto a un repositorio permite mantener el historial de cambios y actualizar el VPS fácilmente ejecutando `git pull`.

1. Clona el repositorio dentro del VPS (ver [2.Git.md](2.Git.md)):

```bash
git clone git@github.com:usuario_git/repositorio.git
```

> [!IMPORTANT]
> **Configuración de clave SSH entre VPS y GitHub:**  
> La clave SSH creada para acceder de tu PC al VPS **no sirve** para que el VPS acceda a GitHub. Debes generar una clave SSH nueva **dentro del VPS** y añadir la clave pública a tu cuenta de GitHub.
> 
> Generar clave SSH en el VPS:
> ```bash
> ssh-keygen -t ed25519 -C "vps-git"
> ```
> Mostrar la clave pública para copiarla en GitHub (*Settings > SSH and GPG keys*):
> ```bash
> cat ~/.ssh/id_ed25519.pub
> ```

## 4. Construir la imagen de Docker

Accede a la carpeta de la aplicación dentro del VPS y ejecuta el proceso de compilación de la imagen:

```bash
cd ~/nombre_carpeta
docker build -t nombre_imagen .
```

### Desglose del comando:

- `docker build`: Lee el `Dockerfile` y empaqueta el entorno a partir de la carpeta en la que estás situado.
- `-t nombre_imagen`: Es la etiqueta que se asigna a **la imagen** para identificarla (el contenedor se nombra después con `--name`).
- `.`: Es el **contexto de construcción**: le dice a Docker que el `Dockerfile` y los archivos a copiar están en la carpeta actual.

### Comandos de verificación:

```bash
# Listar las imágenes que hay actualmente en Docker
docker images

# Inspeccionar los detalles técnicos de una imagen
docker inspect nombre_imagen
```

---

## 5. Ejecutar el contenedor con volumen persistente

Pon en marcha el contenedor vinculando los puertos e indicando un volumen para garantizar que la base de datos (SQLite) y los archivos locales no se pierdan al reiniciar o destruir el contenedor.

```bash
docker run -d --name nombre_contenedor -p 8080:8080 -v ~/nombre_carpeta:/app nombre_imagen
```

### Explicación detallada de los parámetros:

- `docker run`: Arranca un contenedor a partir de una imagen (distinto de `docker build`, que solo la construye; `run` la pone en marcha).
- `-d` (*detached mode*): Ejecuta el contenedor en segundo plano. Sin esto, el contenedor ocuparía tu terminal y si cierras la sesión SSH, se detiene.
- `--name nombre_contenedor`: Le da un nombre al contenedor (no a la imagen — un contenedor es una "instancia en marcha" de la imagen, como una app abierta a partir de un programa instalado). Así luego puedes hacer `docker logs nombre_contenedor`, `docker stop nombre_contenedor` o `docker restart nombre_contenedor` sin acordarte de IDs raros.
- `-p 8080:8080`: Mapea puertos con el formato `puerto_del_vps:puerto_de_dentro_del_contenedor`.
  - El de la izquierda es el que usarás tú desde fuera en el VPS.
  - El de la derecha tiene que coincidir con el que usa `server.py` por dentro (el mismo que pusiste en `EXPOSE`).
- `-v ~/nombre_carpeta:/app`: Monta un **volumen de datos**.
  - Sin esto, si el contenedor se borra o reinicia, se perdería la base de datos SQLite y los archivos generados.
  - Conecta una carpeta real del VPS (izquierda) con una carpeta de dentro del contenedor (derecha), así los datos viven fuera del contenedor y sobreviven aunque el contenedor se elimine.
- `nombre_imagen` (al final, sin `-t`): Aquí ya no es una etiqueta que tú pongas, es el nombre de la imagen que quieres usar para crear el contenedor (el mismo que le diste antes con `docker build -t`).

> [!NOTE]
> **Aislamiento del directorio `/app`:**  
> Si entramos dentro del mismo contenedor con la orden `docker exec -it nombre_contenedor sh`, veremos que hay una carpeta llamada `app`, definida por `WORKDIR /app` en el `Dockerfile`. No es una etiqueta de Docker ni nada reservado por el sistema: cada contenedor tiene su propio `/app` aislado; el mismo nombre puede repetirse en contenedores distintos sin conflicto.

---

## 6. Verificar el funcionamiento local en el VPS

Antes de exponer la aplicación al exterior, comprueba que responde correctamente en la red local del servidor:

```bash
# Comprobar que está "Up" y no en bucle de reinicio
docker ps

# Probar la respuesta HTTP del servidor local
curl http://localhost:8080
```

### Inspección de errores:

Si el contenedor no aparece en `docker ps` o su estado marca *Exited*, revisa la salida de logs para ver qué falla (típicamente un puerto mal indicado o rutas de archivos):

```bash
docker logs nombre_contenedor
```

## 7. Exponer la aplicación con Cloudflare Tunnel

En el mismo `cloudflared` configurado previamente en el VPS (por ejemplo, para [n8n](4.N8n_Docker.md)), solo debes agregar un nuevo hostname público con un subdominio distinto:

1. Abre el panel de control de **Cloudflare Zero Trust** (*Networks > Tunnels*).
2. Selecciona tu túnel activo y edita su configuración.
3. En la sección **Public Hostnames**, añade una nueva regla:
   - **Subdominio / Hostname:** `app.dominio.es` (o el subdominio que elijas)
   - **Service Type:** `HTTP`
   - **URL / Target:** `localhost:8080`
4. Guarda los cambios.

> [!TIP]
> **Túnel único vs. Varios hostnames:**  
> Una vez instalado el token de Cloudflare en una máquina, ese `cloudflared` corre **un solo túnel**. Lo que sí admite ese túnel es **varios hostnames públicos** (subdominios), cada uno apuntando a un puerto local distinto (`http://localhost:8080`, `http://localhost:5678`, etc.).

## 8. ¿Por qué no usamos `docker-compose` en esta aplicación?

`docker-compose` sirve para cuando quieres levantar varios contenedores relacionados a la vez (por ejemplo, n8n + su base de datos + un proxy), definiendo todo en un archivo YAML en vez de escribir varios `docker run` largos a mano.

La aplicación de este ejemplo es un único contenedor autocontenido: un servidor Python sin dependencias externas complejas, sin base de datos independiente (usa SQLite dentro del propio contenedor/volumen), sin necesidad de coordinar nada más. Para este caso, un `docker run` con sus flags (`-d`, `-p`, `-v`) hace exactamente lo mismo que haría un `docker-compose.yml` de un solo servicio, pero en una sola línea de comandos.

### Criterio práctico:

- **1 solo contenedor:** `docker run` es más rápido y directo.
- **2 o más contenedores dependientes entre sí:** `docker-compose` te ahorra trabajo porque recuerda la configuración y te permite arrancar todo con `docker-compose up -d`.

## 9. Procedimiento para actualizar y redesplegar la aplicación

Si necesitas modificar o ampliar la aplicación, sigue estos pasos (la imagen de Docker es una foto fija del código: no cambia solo porque cambien los archivos en la carpeta del VPS):

### Paso 1: Descargar los cambios en el VPS

Tras subir los cambios a Git (`git push` desde tu PC), descárgalos en el VPS:

```bash
cd ~/nombre_carpeta
git pull
```

### Paso 2: Detener y eliminar el contenedor actual

Primero se borra el contenedor que está usando la imagen:

```bash
docker stop nombre_contenedor
docker rm nombre_contenedor
```

*(O de forma abreviada: `docker rm -f nombre_contenedor`)*

### Paso 3: Reconstruir la imagen de Docker

Hay que **volver a construir la imagen** con el código nuevo (este paso es obligatorio, sin él no hay imagen nueva que arrancar):

```bash
cd ~/nombre_carpeta
docker build -t nombre_imagen .
```

### Paso 4: Arrancar el nuevo contenedor

#### Opción 1: Con reinicio automático (Recomendado para producción)
`--restart unless-stopped` hace que el contenedor vuelva a arrancar solo si se reinicia el VPS:

```bash
docker run -d --name nombre_contenedor --restart unless-stopped -p 8080:8080 -v ~/nombre_carpeta:/app nombre_imagen
```

#### Opción 2: Sin reinicio automático

```bash
docker run -d --name nombre_contenedor -p 8080:8080 -v ~/nombre_carpeta:/app nombre_imagen
```
