# Despliegue de una Aplicación Web Python en Docker (VPS)

Guía para meter una aplicación web hecha en Python dentro de un contenedor **Docker**, conservar sus datos con un **volumen**, hacer que **arranque sola si el servidor se reinicia** y publicarla con **Cloudflare Tunnel**.

> [!NOTE]
> Todos los comandos se ejecutan **dentro del VPS**, tras entrar por SSH (ver [1.VPS.md](1.VPS.md)).

**Conceptos básicos (repaso):**
- **Imagen:** la "plantilla" con tu app y todo lo que necesita. Se crea una vez.
- **Contenedor:** la imagen puesta en marcha (como abrir un programa ya instalado).
- **Volumen:** carpeta del VPS conectada a una carpeta del contenedor, para que los datos no se pierdan.

---

## 1. Localizar el archivo de inicio y el puerto

Abre el script que arranca el servidor (`app.py`, `main.py`, `server.py`...) y busca la línea que lo levanta:

- **Flask:** `app.run(host='0.0.0.0', port=8080)`
- **FastAPI / Uvicorn:** `uvicorn.run(app, host='0.0.0.0', port=8080)`
- **http.server:** `HTTPServer(('0.0.0.0', 8080), ...)`

Apunta dos datos: el **archivo** (ej. `server.py`) y el **puerto** (ej. `8080`).

> [!IMPORTANT]
> El host debe ser `0.0.0.0`. Con `127.0.0.1` la app solo se oiría a sí misma dentro del contenedor y no sería accesible desde fuera.

---

## 2. Crear el `Dockerfile`

En la raíz del proyecto crea un archivo llamado `Dockerfile` (sin extensión):

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8080
CMD ["python3", "server.py"]
```

Línea a línea:
- `FROM python:3.12-slim`: parte de una imagen que ya trae Python (versión ligera).
- `WORKDIR /app`: carpeta de trabajo dentro del contenedor; si no existe, se crea.
- `COPY requirements.txt .` y `RUN pip install ...`: copian la lista de librerías e instalan. Se hace **antes** de copiar el código para que Docker reutilice este paso si solo cambias el código.
- `COPY . .`: copia todo tu proyecto a `/app`.
- `EXPOSE 8080`: documenta el puerto que usa la app (es informativo, no lo abre).
- `CMD [...]`: comando que se ejecuta al arrancar el contenedor.

> [!TIP]
> Si tu app **no usa librerías externas** (solo la biblioteca estándar de Python), borra las líneas `COPY requirements.txt .` y `RUN pip install ...`.

---

## 3. Subir el proyecto al VPS

**Opción A: `scp`** (copia directa desde tu PC):

```bash
scp -r carpeta-app usuario@ip_vps:~/nombre_carpeta
```

**Opción B: Git y GitHub (recomendada)**, porque luego actualizas con un simple `git pull`:

```bash
git clone git@github.com:usuario_git/repositorio.git
```

(Más información en [2.Git.md](2.Git.md).)

> [!IMPORTANT]
> El VPS necesita su **propia** clave SSH para hablar con GitHub (la de tu PC no vale). Cómo crearla: [2.Git.md](2.Git.md), apartado 3.

---

## 4. Construir la imagen

```bash
cd ~/nombre_carpeta
docker build -t nombre_imagen .
```

- `docker build`: lee el `Dockerfile` y crea la imagen.
- `-t nombre_imagen`: el nombre (etiqueta) que le das a la imagen.
- `.`: "el `Dockerfile` está en esta carpeta".

Comprobar que existe: `docker images`

> [!NOTE]
> Si usas **Docker Compose** (opción B del punto 5), este paso lo hace Compose por ti y puedes saltarlo.

---

## 5. Ejecutar el contenedor (con volumen y arranque automático)

Hay dos formas de hacerlo. **Elige una**: las dos dan el mismo resultado.

### Qué hace cada parte

| Pieza | Para qué sirve |
|---|---|
| `-d` / segundo plano | El contenedor no ocupa tu terminal y sigue vivo al cerrar SSH. |
| Puerto `8080:8080` | `puerto_del_vps:puerto_del_contenedor`. El de la derecha debe coincidir con el de tu app. |
| Volumen `~/nombre_carpeta:/app` | Conecta una carpeta del VPS con `/app`. Así la base de datos SQLite y los archivos generados viven en el VPS y sobreviven si borras el contenedor. |
| `restart: unless-stopped` | Si el VPS se reinicia (o la app falla), Docker vuelve a arrancar el contenedor solo. |

> [!TIP]
> Se usa `127.0.0.1:8080:8080` en vez de `8080:8080` porque Cloudflare Tunnel está en el mismo VPS. Así la app **solo** se ve desde el propio servidor y no queda abierta a todo Internet (Docker se salta el firewall `ufw` si publicas el puerto sin más).

### Opción A: con `docker run`

```bash
docker run -d --name nombre_contenedor --restart unless-stopped -p 127.0.0.1:8080:8080 -v ~/nombre_carpeta:/app nombre_imagen
```

- `docker run`: crea y arranca un contenedor a partir de una imagen.
- `-d`: segundo plano.
- `--name nombre_contenedor`: nombre del contenedor, para usar luego `docker logs`, `docker stop`, etc.
- `--restart unless-stopped`: arranque automático (se reinicia siempre, salvo que tú lo pares con `docker stop`).
- `-p 127.0.0.1:8080:8080`: puerto, solo accesible desde el VPS.
- `-v ~/nombre_carpeta:/app`: el volumen.
- `nombre_imagen`: la imagen creada en el punto 4.

### Opción B: con Docker Compose

Es lo mismo, pero guardado en un archivo, de modo que no hay que recordar comandos largos. Crea `compose.yaml` en la carpeta del proyecto:

```yaml
services:
  app:
    build: .
    container_name: nombre_contenedor
    restart: unless-stopped
    ports:
      - "127.0.0.1:8080:8080"
    volumes:
      - ./:/app
```

Línea a línea:
- `services:` / `app:`: lista de contenedores; aquí solo uno, llamado `app`.
- `build: .`: construye la imagen con el `Dockerfile` de esta carpeta (equivale al `docker build`).
- `container_name`: nombre del contenedor.
- `restart: unless-stopped`: arranque automático.
- `ports`: igual que `-p`.
- `volumes: ./:/app`: igual que `-v` (`./` es la carpeta del proyecto).

Arrancar (construye y lanza):

```bash
docker compose up -d --build
```

> [!NOTE]
> **¿Cuál elegir?** `docker run` vale para pruebas rápidas. **Compose es mejor para producción**: la configuración queda guardada y versionada en Git, y actualizar es un solo comando. También es la opción cuando hay varios contenedores (app + base de datos...).

### Comprobar que arranca solo tras reiniciar

```bash
sudo reboot
# espera un minuto, vuelve a entrar por SSH y ejecuta:
docker ps
```

Debe aparecer tu contenedor como *Up*. Si no, comprueba que Docker arranca con el sistema: `sudo systemctl enable docker`.

> [!NOTE]
> Si el contenedor ya existía sin reinicio automático, no hace falta recrearlo: `docker update --restart unless-stopped nombre_contenedor`.

---

## 6. Verificar en el VPS

```bash
docker ps                      # ¿aparece como "Up"?
curl http://localhost:8080     # ¿responde la app?
docker logs nombre_contenedor  # si falla: muestra el error
```

Si el estado es *Exited* o se reinicia en bucle, casi siempre es un puerto mal puesto o una ruta de archivo incorrecta, y `docker logs` lo dirá.

---

## 7. Exponer la app con Cloudflare Tunnel

Reutiliza el túnel que ya tienes (ver [Cloudflare.md](Cloudflare.md)). Solo añade un nuevo hostname:

1. **Cloudflare Zero Trust** > *Networks > Tunnels*.
2. Elige tu túnel y pulsa editar.
3. En **Public Hostnames** añade:
   - **Hostname:** `app.dominio.es`
   - **Service Type:** `HTTP`
   - **URL:** `localhost:8080`
4. Guarda.

> [!TIP]
> Un túnel puede tener **varios hostnames**, cada subdominio apuntando a un puerto distinto (`localhost:8080`, `localhost:5678`...).

---

## 8. Actualizar la aplicación

Después de hacer `git push` desde tu PC, en el VPS:

```bash
cd ~/nombre_carpeta
git pull
```

Luego, según cómo la arrancaste:

**Con Docker Compose** (un solo comando):

```bash
docker compose up -d --build
```

**Con `docker run`** (hay que borrar y recrear):

```bash
docker rm -f nombre_contenedor
docker build -t nombre_imagen .
docker run -d --name nombre_contenedor --restart unless-stopped -p 127.0.0.1:8080:8080 -v ~/nombre_carpeta:/app nombre_imagen
```

> [!NOTE]
> Como el volumen monta la carpeta del VPS sobre `/app`, el contenedor ya ve el código nuevo tras el `git pull`; en ese caso a veces basta `docker restart nombre_contenedor`. Reconstruir la imagen es obligatorio si cambias el `Dockerfile` o `requirements.txt`, y es lo más seguro en cualquier caso.
